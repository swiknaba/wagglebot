## Architectural Decisions

### 1. Persisted wire mapping

Create `services/database/db/migrations/20261006120000_complete_memory_wire_mapping.rb`; do not modify `20260916130000_create_memory_schema.rb`.

| Public field | Existing/additive storage | Mapping |
|---|---|---|
| `id` | existing `id text` | UUID string; new IDs satisfy existing schemas |
| `scope` | existing `scopes text[]` | exactly one of `system:<name>`, `domain:<name>`, `org`; no inferred cross-scope merging |
| `content` | existing `text` | original accepted content; format the embedding input separately |
| `confidence` | existing floating `confidence` | `low=0`, `medium=0.5`, `high=1`; decode only these exact values |
| `status` | existing lifecycle columns | active true means active; otherwise invalidated timestamp means invalidated; otherwise superseded-by means superseded; reject an inactive row with neither |
| `wake` | add boolean, NOT NULL, default false | never inferred from confidence/source |
| `reviewAfter` | add nullable `review_after date` | ISO calendar date, omitted when null; required for wake |
| `supersedes` | add nullable `supersedes text` | UUID string when set |
| `supersededBy` | existing `superseded_by` | UUID string when set |
| `provenance` | existing JSONB | immutable entries, stable structural union; actor is checked/replaced from verified identity |
| timestamps | existing timestamps | convert database UTC instants to RFC3339; date field remains date-only |

An active row cannot carry an invalidated timestamp or superseded-by pointer. Invalidation may preserve a supersession pointer because audit history must survive. Wake eligibility additionally requires active, high confidence, and `reviewAfter >= current UTC date`.

The committed initial migration uses timestamps without time zone. Preserve it and adopt an explicit UTC walltime convention: worker database sessions use UTC, writes pass UTC values, and the per-pool timestamp parser interprets those walltimes as UTC. Keep PostgreSQL date values as ISO date strings rather than timezone-dependent JavaScript dates. Existing non-UTC legacy walltimes require explicit operator mapping; never guess their timezone. Tests must prove timestamp/date stability with a non-UTC process timezone.

Add `worker_state jsonb NOT NULL` to the existing singleton embedding metadata row, initially `{ "operations": {}, "sources": {}, "reindex": { "pending": [] } }`. The embedding profile columns retain their existing values and schemaVersion 1. The additive migration does not change embedding dimensions or silently convert legacy IDs, multiple scopes, arbitrary numeric confidence, kinds, or malformed provenance.

Before becoming ready, validate every legacy record through the persisted adapter and `MemoryRecordSchema`. Unsupported data fails startup with a content-free message requesting explicit migration; it must not surface later as an unexplained GET failure. Rollback refuses while the new columns or worker state contain meaningful data; an empty fresh schema can roll back safely. Regenerate the ordered manifest and schema-only dump from the real isolated database.

### 2. Durable idempotency and concurrency

Use the metadata row as the Phase 2 mutation coordination point: `SELECT ... FOR UPDATE`, then record reconciliation/source replacement/admin-state update and ledger insertion in the same PostgreSQL transaction. Release the lock only at commit/rollback. Scan and embed outside the transaction; after locking, re-read any affected records and source state before deciding the write.

Ledger identity is `[principal.kind, principal.username, operationKey]`, encoded unambiguously. Its request hash includes operation name, resource ID/source key, and the schema-normalized request excluding only `operationKey`; recursively sort object keys, preserve semantically ordered arrays. A successful entry stores the hash and original response, not the request prose. Same key/hash returns that response after restart; different hash returns `operation_key_conflict`. Authorize current principal before replaying a prior result. Failed requests do not reserve a successful operation key.

Successful replay is checked through a small read-only repository lookup after strict syntax/hash and current authorization, before new-write-only confirmation/review-date checks, scanning or embedding. Keep the final locked replay check for concurrent first executions. Remember/proposal require current verified user/catalog write authorization before replay; a renewed session may replay its earlier successful proposal without reapplying the earlier confirmation to the new token lifetime. Publication requires the current configured administrator token before replay; source owner is data, so an old successful same-hash result may replay after catalog ownership changes, old-commit removal or wake expiry. Only no-entry publication paths apply current catalog owner/source-binding/ancestry/scanning/embedding rules, revalidated under lock before new writes. Existing request hashes remain stable.

The verified authentication contract has no human/agent role. Keep `Principal` as the verified user/session/catalog identity. For the ledger, `principal.kind` means a trusted internal operation actor namespace, selected by the service method: proposal is `agent`, remember/invalidate is `human`, publication is `git`; administrator operations use a separate operator namespace derived from their configured-token boundary. Encode the tuple with JSON. Neither request fields nor supplied provenance select that namespace. These names describe operation semantics and do not prove that a token holder is a human or an agent; do not invent an auth claim or a new role-based access promise. HTTP and MCP bind the same namespace for the same operation.

No ledger expiry is documented, so do not evict entries or invent TTL semantics. This deliberately serializes writes and rewrites a growing JSON object, suitable for the initial small governed service. Document that operational limit and expose counts/bytes without content; do not claim unlimited throughput. Read/search queries do not acquire this mutation lock. A future ledger storage change is separate work, not justification for extra Phase 2 tables.

### 3. Canonicalization and reconciliation

The public request has title/content, not subject/relation/value. Do not infer those missing fields with a model or accept undocumented fields. Normalize title for identity using Unicode NFC, trim/collapse whitespace, and lowercase. Preserve accepted title/content in the wire record. Compute contentHash as SHA-256 of original UTF-8 content.

Direct identity: `direct:` plus SHA-256 of JSON `[scopeString, kind, normalizedTitle]`. Canonical key: identity plus `:` plus contentHash. New direct record IDs are generated UUIDs and are made stable for retries by the durable transaction ledger/canonical unique key. This avoids falsely promising a SHA-256 ID where the public API requires UUID.

Same canonical key merges maximum confidence and deduplicated provenance; do not silently combine scopes. Changed content in the same active identity slot is rejected if confidence is lower, otherwise supersedes the previous active row and links both records. Explicit same-content remember may reactivate an invalidated/superseded canonical row after all current authorization/scanning checks; clear its inactive markers, supersede any current incumbent, and avoid creating self-links. The audit/provenance history remains. API documentation must state this explicit reactivation behavior and title-based identity rule.

For a same-canonical merge, proposal preserves existing wake/review metadata. Explicit remember applies its schema-normalized `wake` (default false) and optional `reviewAfter` (omitted removes the value), allowing a user to arm, renew or clear wake eligibility through the existing request contract. This also applies to explicit reactivation. Confidence still merges by maximum and provenance by stable union. A newly created different-content row uses its request metadata. Update `updatedAt` for material confidence, provenance, wake/review or lifecycle changes; an exact new-key repeat may return unchanged. These are operation semantics, not authenticated human/agent roles.

A proposal matching an inactive same-canonical row returns `unchanged` with its historical UUID and preserves its inactive state; only explicit remember reactivates that row. A fresh changed-content proposal follows normal reconciliation. Remember reactivation without a current incumbent preserves the historical `supersedes` pointer; with an incumbent it uses that incumbent's ID and never creates a self-link. Invalidating a superseded row sets invalidation state/reason while preserving its supersession pointer; only an already invalidated row is an invalidation no-op. Cancel that record's pending reindex work atomically with invalidation.

Proposal batches prevalidate, authorize, confirm, scan, and embed every fact before one atomic transaction. Confirmation username must equal the verified principal; confirmedAt must be within the session lifetime and not in the future. A proposal can never set wake or escape system scope. System writes are allowed to registered internal users; domain requires owning-group membership, org requires catalog org-owner annotation. Read scopes select relevance for trusted coworkers, rather than enforcing a new cross-team read ACL.

### 4. Search and readiness

Use PostgreSQL array overlap for catalog-validated selected scopes before distance ranking and limit. With omitted or empty explicit scopes, query the supplied system/domain/org cascade. An explicit nonempty scope list is an explicit selection of catalog-valid scopes. Validate cascade consistency against the catalog. Component scope is never persisted.

Query embeds only the caller's bounded query; rank active rows by cosine `<=>` distance, return `1/(1+distance)` scores, default minScore 0.35, stable ID tie-break, maximum 20. Do not add an undocumented public minScore input. Wake never embeds and uses only active high-confidence unexpired wake rows in the cascade, maximum three, deterministic scope-specificity/updatedAt/ID ordering; return additionalEligible using a count before limit. Its record score is 1 because vector relevance is not evaluated.

Startup compares complete ordered migration filenames and fixed embedding metadata, requires exactly one metadata profile row, validates legacy wire mapping, and initializes the CPU provider before accepting memory work. `/livez` remains shallow; `/readyz` checks required dependencies and returns 503 when unavailable. The worker never migrates its own database. SQL values, vectors, and scope arrays are parameterized. Correct the API score comment to name the documented cosine-distance transformation instead of claiming raw cosine similarity; retain its existing 0..1 result schema.

### 5. Reviewed publications and admin compatibility

Source state lives under `worker_state.sources[sourceKey]`: source identity, current revision and canonical-body hash, accepted historical revisions, and current chunk-to-record IDs. It is updated atomically with the records and the operation ledger. Each chunk has a source-specific stable identity; changed text supersedes the old canonical record. Same revision/body is a no-op even with a new operation key; same revision with different body is `operation_key_conflict`. Missing chunks are invalidated in the same transaction. Preserve original source/provenance entries.

Git SHA values have no lexical chronology. Configure a trusted repository-identity-to-checkout map; request repository values must never select arbitrary server filesystem paths or trigger a fetch. An injected revision verifier uses bounded native Git argument arrays to prove the old revision is an ancestor of the new revision in that trusted checkout. Reject ancestor rollback, unrelated histories, unknown commits, and a previously superseded revision with `source_revision_regressed`. Initial publication verifies the supplied commit exists. Source identity (repository/path/scope) cannot be rebound under the same source key. Serialize revision revalidation under the mutation lock; no Git fetch or network runs there.

Publication parser/chunker retains reviewed Markdown verbatim, validates owner/catalog/scope and normalized repository-relative paths, and submits complete sources capped at 256 chunks/1 MiB. A fully removed source needs a zero-chunk complete replacement: remove the existing contract's undocumented `.min(1)` restriction while retaining `.max(256)`, and cover it with regression tests; source state provides identity even when no chunks remain.

Rescan invokes both scanners over canonical persisted material and atomically invalidates newly rejected rows; unavailable scanner fails closed. Its response and stored audit state contain rule IDs/counts only. Reindex accepts only the current known embedding-profile identity, stores pending record IDs/content hashes in `worker_state.reindex`, and returns their queued count. Define that identity as UUIDv5 under the standard URL namespace for `wagglebot:xenova-transformers:all-MiniLM-L6-v2:384:cosine:1`; omitted profileId selects that fixed profile, and a different UUID fails with `embedding_profile_invalid`. Run-once claims up to the documented limit under the singleton lock, embeds outside the lock, then commits only if the record hash is unchanged. Store claim expiry/attempts in that same JSON state; failed or abandoned claims become retryable, with bounded attempts and content-free failure counts. No side-table or worker filesystem queue.

Invalidation changes lifecycle immediately, so search never needs provider deletion. Amend API's obsolete “enqueues provider deletion” text to describe direct exclusion and queued reindex cancellation. Ordinary remember/publication writes embed synchronously and return committed records; they do not wait on admin reindex. `run-once` is admin HTTP only and never an MCP tool.
